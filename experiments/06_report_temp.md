## Final Architecture Decisions
### A. Can questions safely become competency-based instead of role-based?
**YES**. 100% of the questions in the question bank map definitively to a canonical `competency_id`. By uncoupling them from the `Statistical Officer` folder, they can become a generic, global pool.

### B. Should questions be reusable across roles?
**YES**. Competencies like 'Data Quality' and 'Python / Data Analysis' will naturally appear across multiple technical roles. The questions evaluate the *competency*, not the role itself.

### C. Should role blueprints select from competency pools?
**YES**. The blueprint should specify how many questions are needed per required competency. This scales beautifully across 41+ roles.

### D. Should baseline question selection be deterministic or controlled-random?
**RECOMMENDATION: DETERMINISTIC FROM COMPETENCY POOLS (Policy B)**.
For an Initial Baseline assessment, it is critical that everyone in the same role receives the same baseline evaluation. However, the exact IDs should not be hardcoded in the blueprint. The evaluator should deterministically select the first N active questions from the pool using a stable sort (e.g. by `question_id`), ensuring stability while allowing the generic schema to remain uncoupled from specific question IDs.

## Recommended Next Implementation Step
Execute the refactor of `app/assessment/evaluator.py`, `models.py`, and `assessment_blueprints.json` to utilize `competency_id` generic logic (Policy B) instead of role-hardcoded mappings, migrating Statistical Officer to the new format to ensure zero regressions.
